# Runtime compatibility — the contract, the verdict, the gate

The runtime (`~/.hermes/hermes-agent`) follows Nous Research `main`. The app
above it is ours and changes on its own schedule. This page is how the two stay
compatible without ever merging anything.

## The pieces

| Piece | Where | What it is |
|---|---|---|
| Lock | `iclone/contract/runtime.lock.json` | What OUR code consumes: methods + params + result reads, events + payload reads, server requests, error codes, REST, CLI, config keys, env, disk. Names and types only, never values. Reviewed. |
| Sites | `iclone/contract/runtime.lock.sites.json` | Where each consumed name is called. Unreviewed; refactors churn only this file. |
| Spec | `iclone/contract/runtime.spec.json` | What the runtime SERVES at a revision, from `served.py`. |
| Types | `apps/desktop/src/types/runtime-contract.generated.ts` | Generated from a spec (or the union of two, with `since`/`until`). |
| Verify | `apps/desktop/electron/iclone-compat/verify.ts` | The only place go/no-go rules live: `verify(lock, specs) → findings → verdict`. |

The lock is generated by `node iclone/contract/extract.mjs`; nobody edits it by
hand. A non-empty lock diff after a code change is reviewed with a refreshed
`verifiedAgainst` or a waiver in `iclone/contract/waivers.json`
(`{name, reason, ticket, expires}`).

## Provider tiers

- **T1** — the runtime's OpenRPC at the revision. Authoritative: the runtime
  validates every request against it before dispatch.
- **T2** — an AST pass over the runtime's python (`served.py`, stdlib only,
  never imports runtime code). Low confidence: used for revisions that predate
  the OpenRPC, and as a cross-check (`specTier: "openrpc+drift"`).

## Verdict levels

| Level | Meaning | Who can proceed |
|---|---|---|
| GREEN | Every consumed name is served with compatible params and reads | The agent may write a request file; main asks the owner in a native dialog |
| AMBER | Compatible, with changes worth reading (additive keys, deprecations) | The owner only: "Update and accept" |
| RED | Something we consume is gone, renamed or now requires a key we do not send | The owner only, with a 3 s hold; every finding is named and audited |
| UNKNOWN | The spec could not be built or read | The owner only, with a 1.5 s hold. UNKNOWN is never GREEN |

The gate runs in Electron **main**, inside `hermes:updates:apply` — not in the
UI and not in this skill. The pane and the overlay chip only show it.

## Reading the runtime without touching it

The runtime is a `blob:none` promisor clone: a careless `git status` rewrites
its index and a non-HEAD read lazy-fetches over the network. So:

- Read the runtime's HEAD as **files** (`served.py --runtime <checkout>`).
- Read any other revision from the APP repo's `upstream` objects
  (`served.py --repo app/.git --rev <sha>`), with `GIT_NO_LAZY_FETCH=1` and
  `GIT_OPTIONAL_LOCKS=0`.
- Never run `git status`, `git fetch` or `hermes update` against the runtime
  from this skill.

`scripts/contract.sh` does all of this and prints the verdict in ≤ 30 lines.

## When the verdict is RED — fix forward

The runtime lane stays `main`. RED is a "fix the app first" signal:

1. The P0 ADP ticket names the culprit upstream commits (`git log -S'"<name>"'`
   in the app repo). File it the day the break lands upstream.
2. Fix the app with the **dual-path rule**: the fix must pass `verify` against
   BOTH the installed spec and the target spec, branching on what the runtime
   offers (the `client.capabilities` result, method presence in the OpenRPC) —
   never on a version string.
3. Regenerate the lock (`extract.mjs`) and the types (`gen-types.mjs`), rerun
   `scripts/contract.sh --rev <target>` until it is GREEN or AMBER, and ship
   within 72 h or the next block.

Behavioural breaks with an identical schema (a reply that now means something
else) are invisible to static rules; the sandboxed canary
(`iclone/contract/canary/`) runs the candidate runtime from an archive with a
throwaway `HERMES_HOME` and replays scripted turns to catch them.

## Watched doors

Every way the runtime can move gets a verdict after the fact: update receipts
under `~/.hermes/logs/update_receipts/`, and the runtime's reflog (a terminal
`git pull`, Hermes.app). On boot the app checks, in order: the backend's
`/api/health` commit equals HEAD, the OpenRPC hash, the cached verdict for
`(contractHash, lockHash)`, then the live probe (off the boot path; it
validates only and never executes a handler).
